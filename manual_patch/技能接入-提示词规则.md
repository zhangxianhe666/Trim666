# 客户端装了技能（比如 PPT），trim 里能不能用上

## 一句话结论

**能用，但不会自动生效。** 技能是「客户端 agent 的东西」，而跑在 trim 链路上的模型是
上游那个（DeepSeek 网页端），两者本来靠「客户端把技能清单/正文塞进上下文」搭桥，
而 trim 恰好把这座桥拆了。要用手动搭一条「技能入口」规则。

好消息是：**不用把技能搬进提示词**。PPT 技能的全部内容 200KB，但入口只有 1431 字节，
本质是一张路由表——模型照表自己去读需要的那几份就行。

---

## 为什么默认用不上（三处断点）

| # | 断点 | 现状 | 后果 |
|---|---|---|---|
| 1 | 技能清单挂在客户端 system 里 | `drop_client_system: true` | 上游模型**不知道本机有技能**，也不知道触发词 |
| 2 | trim 工具列表里没有 `Skill` | 只有 7 个工具（shell/读写/搜索…） | 就算知道，也**没有工具去加载**技能 |
| 3 | 技能正文靠上下文注入 | 只有工具结果会回传 | 技能正文不会自己飞过去 |

手动搭桥 = 在提示词里复刻 #1（告诉模型"有这个技能、什么时候用"）和 #3（告诉它去哪读），
#2 用现有的 Read/Glob 代替。

---

## 关键发现：技能本身就是「渐进式披露」，正好能塞进 trim 的预算

PPT 技能的结构：

```
skills/workbuddy-pptx/
├── SKILL.md                    1431 字节 ← 只有一张路由表（4 行）
├── references/                 200 KB    ← 真正的知识，按需读
│   ├── create-from-scratch.md  7601 字符
│   ├── design-principle.md     8104 字符
│   ├── story-principle.md      7707 字符
│   ├── edit-existing.md        2598 字符
│   └── component-*.md / designs/*.md
└── scripts/                    edsdk.py / pptx2image.py / doc_image_extractor.py
```

SKILL.md 全文只有 4 行「什么任务读哪个 md」。所以提示词里只要复刻这几行（约 200 字），
模型就会自己 Read 那几份——**这正是技能原本的设计**，不是我们硬凑的。

### 实测数据（都在这台机器上跑过）

| 项 | 实测值 | 对 trim 的意义 |
|---|---|---|
| SKILL.md | 1431 字节 | 路由表，可压成 200 字规则 |
| create-from-scratch.md | 7601 字符 | < 单条截断 8000，**装得下** |
| design-principle.md | 8104 字符 | 超 8000 约 104 字，建议分两段读或把单条提到 9000 |
| story-principle.md | 7707 字符 | 装得下 |
| 三份核心合计 | 23412 字符 | 逼近总预算 24000，**第四份会挤掉最早的** |
| `slidep` | 在 PATH 上（`…\binaries\node\versions\22.22.2-6\slidep`） | 生成动作不依赖 python-pptx / COM |
| `slidep create` 冒烟 | 成功建出 11,866 字节 pptx | 纯 shell 就能跑，不需要客户端参与 |
| 找技能目录 | `find` 扫 0.76 秒 | 可以用 Glob 定位，**不要写死版本号路径** |

## 四个方案，按代价排

| 方案 | 做法 | 代价 | 适合 |
|---|---|---|---|
| **A 技能入口规则**（推荐） | 提示词加 2 条：技能目录在哪 + slidep 怎么用 | 替换原第 9 条后总字数 1765/2000，还余 235 | 想用技能完整能力 |
| **B 精简复刻** | 只抄关键几步（就是现在第 8/9 条那种） | 能力缩水，无设计规范可言 | 任务简单，只求"能出个文件" |
| **C 加 Skill 工具** | 工具列表加 `Skill`，让客户端自己加载技能 | 技能正文作为工具结果回来，仍受 8000 截断；客户端升级可能改 schema | 客户端有 Skill 且你想完全交给它 |
| **D 关掉丢弃 system** | `drop_client_system=false` + `max_system_chars=0` | 放弃精简主旨，长上下文易触发上游风控 | 不推荐 |

**A 和 C 的真正区别**：C 是让客户端把技能正文灌给上游（一次性、不可控、会被截断）；
A 是让上游模型自己按需 Read（分次、可控、还能挑着读）。技能本身是文件，A 更贴合它的设计。

## 方案 A：直接粘这两条

粘贴位置：**提示词页**末尾（`Ctrl+End`）。原有第 9 条（`9) 生成 .pptx：New-Object
-ComObject PowerPoint.Application …`）**要删掉**——它和新规则互相打架，
留着模型会在 COM 和技能之间反复横跳。

```text
10) 做 PPT/幻灯片/pptx 不要用 COM 或 python-pptx，改走本机 WorkBuddy 的 PPT 技能：
    先 Glob `**/skills/workbuddy-pptx/SKILL.md`（path 用
    %USERPROFILE%\.workbuddy\plugins\cache，版本号别写死），读它拿到路由表，再只读
    references 里需要的一份：新建=create-from-scratch.md、改稿=edit-existing.md、
    读懂=understand.md；design-principle.md 8104 字符，用 Read 的 offset/limit 分两段读。
    生成用 slidep：create "<pptx>" → 写 slides\NN.slide → upsert-dsl "<pptx>"
    --dsl-file "slides\NN.slide" → lint "<pptx>" --dsl-file "slides\NN.slide"
    --page-index N，有 diagnostics 就改页重提。slidep 不在 PATH 时用
    %USERPROFILE%\.workbuddy\binaries\node\versions\<版本>\slidep。
11) 技能文档里的工具名本环境没有：write_to_file→Write，present_files/TaskCreate 跳过继续，
    bash 命令改 PowerShell 语法。
```

**第 11 条不是可选项，漏了必踩坑。** 技能文档里到处是
`present_files`（打开预览）、`write_to_file`（写页文件）、`TaskCreate`（建任务），
还有 bash 代码块。这些名字不在 trim 的工具清单里，模型真去调的时候会被网关
当未知工具丢掉——日志里会出现「忽略未知工具名: present_files」——模型拿不到任何结果，
就在那里反复重试。实测这条丢工具的行为是确定的（`extract_tool_calls` 只认
配置里那 7 个名字）。

字数核算（按真实提示词 1195 字算）：删掉第 9 条 −129 字，加这两条 +699 字 →
**1765 / 2000**，余 235。若你坚持只追加不删，是 1895 / 2000，也塞得下，但会有冲突。

## 换成别的技能，四步照做

以「装了 docx 技能」「装了 excel 技能」为例，改法完全一样：

1. **找到入口文件**：Glob `**/skills/<技能名>/SKILL.md`（path 同上）。
   先在文件管理器里手动确认它存在，别让模型瞎猜目录名。
2. **只抄路由表，不抄正文**：打开 SKILL.md，通常就几行「什么任务 → 读哪个 md」。
   把这几行改写成一条提示词规则即可。**绝不要**把 references 全文抄进提示词
   （2000 字上限根本装不下，而且大部分页用不到）。
3. **记下它依赖什么命令**：像 `slidep`、`scripts/xxx.py`、`python3` 这种。
   自己先在 PowerShell 里手动跑一次，确认能跑通、记下绝对路径兜底方案。
4. **写工具名映射**：看技能文档里提到了哪些工具（`write_to_file`、`present_files`、
   `TaskCreate`、`edit_file`…），逐个映射到 trim 的 7 个工具或"跳过"。

### 通用模板（填空即可）

```text
10) 做 {{任务类型}} 时不要用 {{原来那条土办法（COM/python-pptx）}}，改走本机
    {{技能名}} 技能：先 Glob `**/skills/{{技能目录名}}/SKILL.md`（path 用
    %USERPROFILE%\.workbuddy\plugins\cache，版本号别写死），读它拿到路由表，再只读
    references 里需要的一份：{{任务A}}={{文件A}}、{{任务B}}={{文件B}}。
    执行用 {{命令名}}：{{命令1}} / {{命令2}}；命令不在 PATH 时用
    %USERPROFILE%\.workbuddy\binaries\{{node 或 python}}\versions\<版本>\{{命令名}}。
11) 技能文档里的工具名本环境没有：{{名字映射}}；bash 命令改 PowerShell 语法。
```

## 坑（都是实际会撞上的）

- **技能升级后目录变了**：`workbuddy-pptx/5.8.3-wb.41334564…/` 这段带版本号，
  升级就变。所以规则里必须用 Glob 定位，写死路径下次必挂。
- **客户端是 DSH 时没有 slidep**：PATH 是 WorkBuddy 的托管 node 环境加的，
  DSH 的 shell 里可能找不到。规则里那条"绝对路径兜底"就是为这个留的；
  也可以先跑 `Get-Command slidep` 探一下。
- **读满三份 references 后第四份会被挤掉**：总预算 24000 是滚动窗口，
  读第四份时最早那份会被丢，模型就"忘了"前面的要求。要真同时装四份，
  把 `工具历史总字符预算` 提到 32000（代价是更接近上游长上下文风控）。
- **技能里的人机交互步骤会退化**：create-from-scratch 里有"风格预览卡""需求澄清
  ≤3 个问题"这类交互，在纯工具链里模型通常直接跳过、一把出稿。想要那套体验，
  得在提示词里单独要求"先给 3 个风格选项让我选"。
- **别同时保留土办法**：原第 9 条（COM 生成）和新规则并存时，模型会在两条路之间
  抖动，表现为"有时用 COM 有时读技能"，很难排查。二选一。
